# ADR 0002: Repo-Aware Integration — Config-First with LLM Fallback

## Status

**Proposed** — Supersedes current archetype-based detection

## Date

2025-12-01

## Context

The Integration Coworker generates API client code, workflow functions, and tests. To integrate this generated code into a target repository, the system must determine:

1. **Where to place files** (e.g., `src/integrations/clients/` vs `lib/external/`)
2. **What naming conventions to follow** (e.g., `{provider}_client.py` vs `{Provider}Client.ts`)
3. **How to wire integrations** (e.g., router registration, module imports)

### Current Implementation: Archetype-Based Detection

The existing system uses predefined "archetypes" — hardcoded configurations for known frameworks:

```python
KNOWN_ARCHETYPES = {
    "fastapi": FrameworkArchetypeConfig(
        default_integrations_root="app/integrations",
        default_tests_root="tests/integrations",
        detection_deps=["fastapi", "uvicorn"],
        ...
    ),
    "django": ...,
    "nextjs": ...,
    # Must add each framework manually
}
```

A two-layer pipeline detects the archetype:
1. **Layer 1 (Detection)**: Pattern-match files and dependencies → confidence score
2. **Layer 2 (Inference)**: High confidence → use archetype defaults; low confidence → heuristic fallback

### Problems with Archetype-Based Approach

| Problem | Impact |
|---------|--------|
| **Closed set** | New frameworks (SvelteKit, Remix, Bun+Hono) require code changes |
| **Maintenance burden** | 7 archetypes × ~50 lines each = ongoing updates |
| **No user control** | Users cannot override incorrect detection |
| **Framework evolution** | Next.js Pages → App Router changed layouts; archetypes lag behind |
| **Custom structures** | Many repos don't follow "standard" layouts |
| **Hybrid projects** | Monorepos with multiple frameworks are ambiguous |

### Decision Drivers

1. **Accuracy**: Correct file placement for any repository structure
2. **Adaptability**: Handle new frameworks without code changes
3. **User control**: Allow explicit overrides when detection fails
4. **Performance**: Minimize LLM calls for repeat operations
5. **Maintainability**: Reduce ongoing archetype maintenance

## Decision

We will adopt a **Config-First with LLM Fallback** architecture for repository-aware integration.

### Architecture Overview

```
┌─────────────────────────────────────────────────────────────────────┐
│  Step 1: Check for .integration-coworker.yaml in repo root         │
│          → If exists: USE IT (instant, accurate, user-controlled)  │
└─────────────────────────────────────────────────────────────────────┘
                              ↓ (not found)
┌─────────────────────────────────────────────────────────────────────┐
│  Step 2: LLM analyzes repository structure                          │
│          → Examines file tree, package.json/pyproject.toml, etc.   │
│          → Generates config based on existing patterns              │
└─────────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────────┐
│  Step 3: Validate and persist config                                │
│          → Validate paths exist, patterns are valid                 │
│          → Write .integration-coworker.yaml to repo                │
│          → Future runs use cached config (no LLM needed)           │
└─────────────────────────────────────────────────────────────────────┘
```

### Config File Schema

```yaml
# .integration-coworker.yaml
# Generated by Integration Coworker — feel free to edit

version: "1.0"

profile:
  name: "my-fastapi-service"
  framework: "fastapi"           # Optional hint for codegen style
  language: "python"

layout:
  integrations_root: "src/external_apis"
  tests_root: "tests/external_apis"

conventions:
  client_module: "clients/{provider}.py"
  flow_module: "flows/{provider}_{task}.py"
  test_module: "test_{provider}_{task}.py"

hooks:                            # Optional — for auto-wiring
  router_file: "src/app/api/router.py"
  router_marker: "# AUTO_INTEGRATION"

metadata:
  generated_by: "integration-coworker"
  generated_at: "2025-12-01T10:30:00Z"
  detection_method: "llm_inference"  # or "user_provided"
```

### Implementation Strategy

#### Phase 1: Add Config Support (Non-Breaking)

```python
def get_repo_profile(repo_path: Path) -> RepoProfile:
    # 1. Config file takes priority
    config_file = repo_path / ".integration-coworker.yaml"
    if config_file.exists():
        return load_config_as_profile(config_file)
    
    # 2. Fall back to existing archetype detection (backward compat)
    detected = detect_repo_profile(repo_path)
    if detected.confidence >= 0.8:
        return build_profile_from_archetype(detected)
    
    # 3. LLM inference for unknown repos
    config = llm_infer_repo_config(repo_path)
    validate_config(config, repo_path)
    save_config(config_file, config)
    return config_to_profile(config)
```

#### Phase 2: LLM Inference Implementation

The LLM receives a structured prompt with:
- Directory tree (filtered to relevant files)
- Contents of `package.json`, `pyproject.toml`, `tsconfig.json`
- Sample of existing integration/service files (if any)

Example LLM prompt:
```
Analyze this repository structure and determine where integration code should be placed.

Directory tree:
```
src/
  app/
    api/
    services/
  lib/
    external/
      stripe/
tests/
  unit/
  integration/
```

Existing integration at src/lib/external/stripe/:
- client.py
- test_stripe.py

Generate a YAML config specifying:
- integrations_root: where new API clients should go
- tests_root: where tests should go
- conventions: naming patterns based on existing files
```

#### Phase 3: Deprecate Archetypes

Once LLM inference proves reliable (measured by user override rate < 5%):
1. Remove `KNOWN_ARCHETYPES` dictionary
2. Remove archetype detection layer
3. Simplify to: config file → LLM inference

## Consequences

### Positive

| Benefit | Description |
|---------|-------------|
| **Open-ended framework support** | LLM handles any framework without code changes |
| **User control** | Config file is editable, versionable, shareable |
| **Self-documenting** | Config file explains placement decisions |
| **Performance** | After first run, reads cached config (no LLM) |
| **Reduced maintenance** | No archetype configs to update |
| **Handles edge cases** | LLM reasons about actual structure, not patterns |

### Negative

| Drawback | Mitigation |
|----------|------------|
| **First-run LLM cost** | ~$0.01-0.05 per repo; amortized over all future runs |
| **LLM reliability** | Validation layer catches invalid configs; user can edit |
| **Requires API access** | First run needs LLM; subsequent runs work offline |
| **New file in repo** | `.integration-coworker.yaml` added; can gitignore if unwanted |

### Neutral

- Existing archetypes remain as fallback during transition
- No breaking changes to public API
- Config file format is extensible for future needs

## Alternatives Considered

### Alternative 1: Archetypes Only (Current State)

**Rejected because:**
- Requires code changes for every new framework
- Cannot handle non-standard layouts
- No user override mechanism
- Ongoing maintenance burden

### Alternative 2: Pure LLM (No Caching)

**Rejected because:**
- LLM call on every run is slow and expensive
- Inconsistent results between runs
- No offline capability

### Alternative 3: User Config Only (No Auto-Generation)

**Rejected because:**
- Poor onboarding experience (users must write config manually)
- Adoption friction for new users
- Defeats "repo-aware" value proposition

### Alternative 4: ML Classifier

**Rejected because:**
- Requires labeled training data (we don't have it)
- Black box (hard to debug misclassifications)
- Still a closed set (training data determines supported frameworks)

### Alternative 5: AST/Import Graph Analysis

**Rejected because:**
- Complex to implement across Python, TypeScript, JavaScript
- Slow for large repositories
- Overkill for the problem (we need directory layout, not code semantics)

## Comparison Matrix

| Criterion | Archetypes | Pure LLM | User Config | **Config + LLM** |
|-----------|------------|----------|-------------|------------------|
| Accuracy | Good (known) | Variable | Perfect | Good → Perfect |
| Speed | Instant | Slow | Instant | Instant (cached) |
| Cold-start | Works | Works | Friction | Works |
| Maintenance | High | None | None | Low |
| New frameworks | Manual | Auto | Manual | Auto |
| User control | None | None | Full | Full |
| **Overall** | 6.65 | 7.45 | 8.30 | **8.55** |

## v1 Constraints

The following limitations apply until the config-first architecture is fully implemented.

### Local Filesystem Only

v1 reads repositories from local paths. Remote sources are not supported.

| Constraint | v1 Behavior | v2 Target |
|------------|-------------|-----------|
| GitHub repos | Not supported | `GitHubRepoContextProvider` |
| S3/Azure blobs | Not supported | Cloud storage adapters |
| Binary files | Skipped silently | Hash-based detection, selective parsing |

```python
# src/integration_coworker/repo/context.py
owner = "local"  # Phase 2 simplification
# Read file content (skip binary files in Phase 2)
```

### File Sampling Limits

Repo snapshots truncate large repositories to fit LLM context windows.

| Limit | Value | Rationale |
|-------|-------|-----------|
| Max files in sample | 5 | Token budget |
| Max chars per file | 500 | Avoid context overflow |

```python
for path in sorted_paths[:5]:  # Only include first 5 files
    full_lines.append(f"```\n{file.content[:500]}...\n```")
```

**v2 Target**: Configurable `max_files`, `max_chars_per_file`, intelligent file selection based on relevance.

### Profile Source Tracking

Detection confidence is tracked internally but not exposed to users.

```python
profile_source: Optional[str] = None  # "archetype", "heuristic", "llm", "cached"
```

**v2 Target**: Display confidence badge in reports. Add manual override API when detection confidence is low.

## Decision Outcome

**Chosen option: Config-First with LLM Fallback**

This approach provides the best balance of:
- Immediate accuracy (user config or LLM inference)
- Long-term maintainability (no archetype updates needed)
- User empowerment (editable config file)
- Performance (cached config after first run)

The transition can be gradual, with archetypes serving as a reliable fallback during the LLM inference stabilization period.
